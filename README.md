# LMS System

**LMS System** — backend-приложение для платформы онлайн-обучения, разработанное на Django и Django REST Framework.

Проект предоставляет REST API для работы с пользователями, курсами, уроками, подписками и платежами. Для аутентификации используется JWT, для оплаты курсов — Stripe Checkout, а фоновые и периодические задачи выполняются через Celery и Redis.

## Основные возможности

### Пользователи

В проекте используется собственная модель пользователя с авторизацией по email.

Реализованы:

- регистрация пользователей;
- JWT-аутентификация;
- обновление access-токена через refresh-токен;
- просмотр списка пользователей;
- просмотр профиля;
- редактирование собственного профиля;
- удаление собственной учётной записи;
- история платежей пользователя;
- автоматическая блокировка пользователей, которые не заходили в систему более 30 дней.

### Курсы

Для курсов реализован CRUD:

- создание;
- получение списка;
- просмотр отдельного курса;
- редактирование;
- удаление.

Курс содержит владельца, название, описание, изображение-превью, стоимость и дату последнего обновления материалов.

Обычный пользователь работает только со своими учебными материалами. Модераторы могут просматривать и редактировать материалы, но не могут создавать или удалять их.

### Уроки

Уроки привязаны к курсам и поддерживают создание, просмотр, редактирование и удаление.

Урок содержит:

- владельца;
- курс;
- название;
- описание;
- изображение-превью;
- ссылку на видео.

Для ссылок на видео реализована валидация: разрешены ссылки только на YouTube.

Изменение урока считается обновлением материалов соответствующего курса и обновляет время изменения курса.

### Подписки на обновления

Пользователь может подписаться на обновления конкретного курса и отменить подписку.

Для пары `пользователь + курс` может существовать только одна подписка.

После обновления материалов курса подписчикам отправляется уведомление по email в фоновой Celery-задаче. Уведомление ставится в очередь только после успешного сохранения изменений.

Чтобы избежать слишком частых рассылок при последовательном редактировании нескольких уроков, уведомление отправляется только в том случае, если с предыдущего обновления материалов курса прошло не менее четырёх часов.

### Платежи

В проекте реализована модель платежей. Платёж связан с пользователем и одним объектом оплаты: курсом или уроком.

Сохраняются:

- пользователь;
- дата платежа;
- оплаченный курс или урок;
- сумма;
- способ оплаты;
- данные Stripe для онлайн-платежей;
- текущий статус платежа.

Для списка платежей поддерживаются фильтры:

```text
paid_course
paid_lesson
payment_method
```

и сортировка по:

```text
payment_date
```

### Stripe Checkout

При создании оплаты курса приложение выполняет следующий процесс:

```text
Course
  ↓
Stripe Product
  ↓
Stripe Price
  ↓
Stripe Checkout Session
  ↓
Payment в локальной базе данных
  ↓
Checkout URL
```

В платеже сохраняются:

- Stripe Product ID;
- Stripe Price ID;
- Stripe Checkout Session ID;
- Checkout URL;
- статус платежа.

Стоимость курса хранится в рублях, а перед передачей в Stripe преобразуется в копейки.

Пример:

```text
1500.00 ₽ → 150000
```

Также реализовано получение актуального статуса Stripe Checkout Session с последующей синхронизацией локальной модели платежа.

Работа со Stripe вынесена в отдельный сервисный слой.

## Celery и фоновые задачи

Для выполнения фоновых задач используется **Celery**, а Redis применяется как broker и result backend.

В проекте реализованы две основные фоновые задачи.

### Уведомление об обновлении курса

После успешного обновления курса или одного из его уроков Celery-задача отправляет email пользователям, подписанным именно на этот курс.

Особенности:

- задача вызывается только после успешного сохранения изменений;
- в очередь передаётся идентификатор курса, а не экземпляр Django-модели;
- подписчики выбираются по конкретному курсу;
- повторная рассылка ограничена интервалом в четыре часа;
- используется timezone-aware время через `django.utils.timezone`.

### Блокировка неактивных пользователей

Celery Beat периодически проверяет поле `last_login` пользователей.

Если активный пользователь не входил в систему более 30 дней, его `is_active` переводится в `False`.

Обновление выполняется одной batch-операцией через QuerySet `update()`, без сохранения пользователей по одному в цикле.

Пользователи с `last_login=None` автоматически не блокируются только на основании этой проверки.
